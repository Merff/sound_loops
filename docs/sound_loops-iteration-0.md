# sound_loops — итерация 0: каркас и случайный саундтрек

## Контекст

Пет-проект: подбор музыки к немым коротким видео-лупам. Финальная цель, до которой мы дойдём за несколько итераций, — агент, который анализирует видео и подбирает подходящий трек по смыслу и настроению.

Итерация 0 строит только транспорт: из базы берутся луп и трек, ffmpeg склеивает превью. Музыка выбирается случайно — это осознанный baseline, с которым будут сравниваться следующие версии.

## Цель

CLI, который собирает mp4: немой луп плюс случайный отрезок случайного трека, подрезанный под длительность этого лупа. Факт рендера сохраняется в базе.

## Definition of Done

1. Схема создаётся в существующей базе; повторный запуск не падает.
2. Ингест заполняет таблицы лупов и треков; повторный запуск не создаёт дубликатов.
3. Рендер несколько раз подряд выдаёт mp4, которые открываются в QuickTime со звуком, и длительность каждого совпадает с длительностью исходного лупа.
4. В таблице рендеров появились соответствующие записи.
5. Линтер и тесты проходят.

Все пункты выполнены и перепроверены после каждой из последующих переделок дизайна (см. ниже).

## Окружение

PostgreSQL уже установлен и запущен локально — ставить не нужно, использовать существующий инстанс и создать в нём отдельную базу. Строка подключения берётся из `.env`, в репозитории лежит `.env.example`.

Остальное: ffmpeg, uv, Python 3.12. Зависимости — CLI (`click`), драйвер Postgres (`psycopg` v3, без ORM), валидация конфига (`pydantic-settings`), менеджер миграций (`yoyo-migrations`), линтер (`ruff`) и тесты (`pytest`).

## Данные

`data/` целиком в `.gitignore`.

**Лупы** — готовые mp4 в `data/loops/`. Готовятся вручную вне проекта: длительность от 3 до 10 секунд, без аудиодорожки. Код их не создаёт и не изменяет, только сканирует и читает метаданные. Файл, который не подходит под эти условия, логируется и пропускается — весь прогон из-за него падать не должен.

**Музыка** — датасет FMA (Free Music Archive), выкладка легально распространяемой музыки, которую поддерживает лаборатория EPFL. Подмножество `fma_small` — это 8 000 тридцатисекундных отрывков в mp3, по 8 сбалансированным жанрам, 7,2 ГиБ. Метаданные лежат отдельно: архив `fma_metadata.zip` (342 МиБ), где `tracks.csv` содержит название, исполнителя, жанры и теги для всех 106 574 треков.

Перед скачиванием треков и мета оценить сколько понадобится диска. На практике для итерации 0 хватило 268 mp3 и одного файла `tracks.csv` — оба архива отдаются с поддержкой HTTP Range, поэтому вместо полной загрузки (7,2 ГиБ + 342 МиБ) были вытащены точечно только нужные записи (`zipfile.ZipFile` поверх кастомного `io.RawIOBase`, читающего диапазоны по HTTP) — экономия в сотни раз по трафику и месту на диске.

Раскладка после распаковки: `data/raw/fma_small/000/000002.mp3`, то есть mp3 разложены по трёхзначным подпапкам, а имя файла — шестизначный ID трека. По этому ID строка находится в `tracks.csv`. Директория сканируется рекурсивно.

У `tracks.csv` три строки заголовка: два уровня колонок (категория/поле — `track`/`title`, `artist`/`name`, `track`/`genre_top` и т.д.), а третья строка — служебная (`track_id,,,...`), не несущая данных. Разбор нужен только для title/artist/genre и не критичен для итерации 0: если формат отличается от ожидаемого, поля остаются пустыми — это не ошибка, код продолжает работу.

Для итерации 0 хватило 200–300 mp3, распаковывать весь архив не понадобилось.

## Модель данных

Три сущности:

- **лупы** — путь, длительность, разрешение;
- **треки** — путь, длительность, метаданные из датасета;
- **рендеры** — какой луп с каким треком склеен, координаты вырезанного отрезка (`track_id`, `start_seconds`) и куда сохранён результат.

Путь — естественный ключ уникальности для лупов и треков, ингест на нём идемпотентен.

Схема управляется миграциями (`yoyo-migrations`): изменение схемы — это новый пронумерованный файл в `src/sound_loops/migrations/`, а не правка одного общего DDL-скрипта.

## Что должен уметь код

**Ингест.** Обойти директории с лупами и музыкой, вытащить метаданные через ffprobe, разложить по таблицам лупов и треков. В конце напечатать, сколько добавлено и сколько пропущено с причинами.

**Рендер.** Взять луп (по пути или случайный), взять случайный трек, которого хватит на длительность лупа, выбрать случайную точку начала внутри него, вырезать из него аудио ровно под длительность лупа, склеить с видео без перекодирования видеопотока, сохранить результат и запись в базу (луп, трек, координаты отрезка), вывести путь.

Два требования к качеству склейки, которые легко упустить:

- на краях вырезанного аудио нужны короткие фейды, иначе каждое превью начинается и заканчивается щелчком и звучит как брак независимо от того, насколько удачна музыка;
- длительность результата определяется видео: если отрезок аудио длиннее лупа, лишнее обрезается.

С ffmpeg и ffprobe работать через subprocess, без питоновских обёрток поверх — команда должна оставаться читаемой и копируемой в терминал. Ошибки бинарей пробрасывать с содержательным сообщением, а не с голым кодом возврата. Тот же принцип — никаких обёрток поверх внешнего инструмента там, где хватает прямого вызова — распространяется и на работу с базой: везде сырой SQL через `psycopg`, без ORM.

## Тесты

Работают на настоящем Postgres — отдельная тестовая база в том же локальном инстансе, создаётся и мигрируется автоматически при первом запуске. Синтетические видео/аудио для тестов генерируются самим ffmpeg (`lavfi`), не зависят от реального датасета; повторяющиеся по длительности файлы кэшируются на уровне тестовой сессии, чтобы не гонять ffmpeg заново на каждый тест.

Проверяется: вырезанное аудио имеет ожидаемую длительность, склеенный файл содержит оба потока, случайная точка начала отрезка всегда попадает в допустимые границы трека, разбор `tracks.csv` (в том числе отсутствующий/битый файл), валидация конфига, идемпотентность миграций и ингеста, и что повторные рендеры каждый раз создают ровно одну новую запись без дублей и сирот.
