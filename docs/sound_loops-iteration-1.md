# sound_loops — итерация 1: музыкальный индекс и поиск по тексту

## Контекст

Продолжение проекта sound_loops. Итерация 0 уже сделана: есть база с лупами и треками, есть CLI, который склеивает превью со случайным треком.

Итерация 1 добавляет смысл в выбор музыки. Треки превращаются в векторы через CLAP — модель, которая раскладывает аудио и текст в одно общее пространство. После этого текстовый запрос вроде «sad piano» можно сравнивать напрямую с аудио и находить похожее.

Сейчас задача — убедиться, что поиск музыки по описанию вообще работает, и услышать это своими ушами.

Железо: MacBook M3 Pro, 18 ГБ, Apple Silicon (MPS).

## Цель

CLI-команда поиска: на вход текстовое описание, на выходе список наиболее подходящих Треков, которые можно тут же прослушать.

## Definition of Done

1. Команда индексации считает эмбеддинги для всех треков в базе; повторный запуск пересчитывает только новые.
2. Индексация прерывается и возобновляется без потери уже посчитанного.
3. Поиск по запросу выдаёт топ-N треков с оценкой похожести и путями к файлам, которые можно прослушать.
4. Проходит проверка вменяемости (см. ниже): на контрастных запросах выдача явно различается и совпадает со здравым смыслом.

## Модель

Использовать CLAP через `transformers` (`ClapModel` и `ClapProcessor`), а не пакет `laion_clap` с PyPI: последний давно не обновлялся и тянет за собой жёсткие пины на старые версии numpy и transformers, что на свежем окружении почти гарантированно ломается.

**Чекпоинт: `laion/larger_clap_general`.**

Напрашивающийся по названию `laion/larger_clap_music` брать не нужно. Есть [публично описанная проблема](https://github.com/embeddings-benchmark/mteb/issues/5069): у этого чекпоинта <cite index="9-1">текстовая башня возвращает практически одинаковый эмбеддинг независимо от входа — средняя попарная косинусная близость между несвязанными фразами составляет 0,9993, а на задаче audio-text retrieval модель работает хуже случайного бейзлайна</cite>. <cite index="9-1">У `laion/clap-htsat-unfused` и `laion/larger_clap_general` те же измерения дают 0,180 и 0,294 соответственно, то есть осмысленно разные представления для разных входов</cite>.

Для нашей задачи это критично: весь поиск строится именно на текстовой башне. Сломайся она — выдача будет выглядеть правдоподобно (что-то же находится), но окажется мусором.

Считать пробовать на MPS, при ошибках откатываться на CPU — модель небольшая, разница не критична. Устройство сделать настраиваемым.

## Что добавляется в схему

Расширение `vector`, колонка под эмбеддинг трека и HNSW-индекс по косинусной метрике.

Эмбеддинги нормализовать перед сохранением. Тогда косинусная близость сводится к скалярному произведению, а сравнение результатов между запусками становится предсказуемым.

Отдельно стоит хранить, какой моделью посчитан эмбеддинг. На следующих итерациях чекпоинт может смениться, и без этого поля невозможно понять, что в базе лежит вперемешку.

## Что должен уметь код

**Индексация.** Взять из базы треки без эмбеддинга, декодировать, посчитать батчами, записать.

**Поиск.** Текст запроса → эмбеддинг текстовой башней → поиск ближайших в pgvector → вывод топ-N с оценкой похожести, названием трека (если метаданные есть).

**Прослушивание.** Главное требование итерации — возможность услышать результат. Команда поиска должна уметь выгружать найденные треки в отдельную папку и, опционально, сразу открывать их системным плеером через `open` на macOS. Читать цифры похожести без возможности послушать бесполезно: только на слух видно, что модель считает «эпичным» или «грустным».

## Проверка вменяемости

Перед тем как доверять выдаче, обязательно прогнать две быстрые проверки. Обе стоит оформить как команду или тест, потому что к ним придётся возвращаться при смене чекпоинта.

**Текстовая башня жива.** Посчитать эмбеддинги нескольких заведомо непохожих фраз (тяжёлый гитарный рифф, медленная грустная фортепианная баллада, женский оперный вокал, быстрая электронная танцевальная музыка) и посмотреть попарные близости. Если все пары около 0,99 — башня схлопнута, чекпоинт негодный, дальше идти бессмысленно.

**Выдача осмысленна.** Прогнать десяток контрастных запросов (спокойное и агрессивное, с вокалом и инструментальное, быстрое и медленное) и послушать топ-3 по каждому. На глаз и на слух оценить, попадает ли модель. Результат записать в README как честное наблюдение, включая то, что получается плохо. На следующих итерациях это станет отправной точкой для нормальных метрик.
