# sound_loops

Пет-проект: подбор музыки к немым коротким видео-лупам. Финальная MVP-версия
— агент на LangGraph: смотрит на кадры лупа, сам вызывает поиск по музыке,
собирает три варианта, а если не понравилось — принимает текстовую обратную
связь («мрачнее», «без вокала») и подбирает заново. Сверху — веб-интерфейс
на Gradio.

До этого было пять итераций, каждая добавляла один слой:

0. **Транспорт** — из базы берётся луп и отрезок трека, ffmpeg склеивает
   превью в mp4, музыка выбирается случайно.
1. **Смысл** — треки превращаются в эмбеддинги через
   [CLAP](https://github.com/LAION-AI/CLAP), текстовый запрос вроде «sad
   piano» сравнивается напрямую с аудио через
   [pgvector](https://github.com/pgvector/pgvector).
2. **Автоматизация** — запрос для поиска формулирует не человек, а VLM,
   посмотрев на кадры лупа.
3. **Измерение** — размеченный набор из 30 лупов, `eval-run`/`eval-compare`/
   `blind-eval`, honest baseline.
4. **RAG** — атрибуты треков (темп, теги), гибридный поиск с фильтрами,
   переранжирование моделью с объяснением.
5. **Агент** (этот README) — линейная цепочка становится графом
   [LangGraph](https://langchain-ai.github.io/langgraph/) с явным
   состоянием: поиск — инструмент, который модель вызывает сама, три
   варианта вместо одного, обратная связь меняет следующую подборку,
   сессия переживает перезапуск процесса (Postgres-чекпойнтер).

Подробности и результаты каждой итерации — `docs/sound_loops-iteration-N.md`.

## Что нужно установить

- Python 3.12
- [uv](https://docs.astral.sh/uv/)
- ffmpeg / ffprobe (например, `brew install ffmpeg`)
- PostgreSQL — предполагается, что локальный инстанс уже установлен и
  запущен; проект создаёт в нём отдельную базу, устанавливать PostgreSQL
  не нужно.
- Расширение [pgvector](https://github.com/pgvector/pgvector) для этого
  инстанса Postgres. Готового бинарного пакета под все версии Postgres в
  brew может не быть (например, для `postgresql@15` есть бандлы только под
  17/18) — тогда собрать из исходников под свою версию:

  ```bash
  git clone --depth 1 --branch v0.8.0 https://github.com/pgvector/pgvector.git
  cd pgvector
  make PG_CONFIG=$(brew --prefix postgresql@15)/bin/pg_config
  make install PG_CONFIG=$(brew --prefix postgresql@15)/bin/pg_config
  ```

  (замените `postgresql@15` на свою версию). `make init-db` сам делает
  `CREATE EXTENSION vector` в миграции — собрать расширение нужно один раз
  заранее, руками ничего создавать не надо.
- [Ollama](https://ollama.com/) — локальный сервер для VLM (нужен для
  `analyze`/`match`/`ui`/`eval-run`/`blind-eval`, не для `render`/`search`):

  ```bash
  brew install ollama
  brew services start ollama       # слушает localhost:11434
  ollama pull qwen3-vl:4b-instruct # ~3.3ГиБ
  ```

  Модель по умолчанию — `qwen3-vl:4b-instruct` (`VLM_MODEL` в `.env`, если
  нужна другая) — среди vision-моделей в Ollama это одна из немногих, что
  совмещает зрение и вызов инструментов в одной модели (см. «Агент и
  веб-интерфейс» ниже, откуда это важно).

Установить зависимости проекта:

```bash
make sync
```

## Как поднять базу

Скопировать `.env.example` в `.env` и указать строку подключения к уже
работающему локальному Postgres:

```bash
cp .env.example .env
```

Создать базу и накатить миграции (идемпотентно — повторный запуск не
падает и не применяет уже применённые миграции повторно):

```bash
make init-db
```

Схема управляется через [yoyo](https://ollycope.com/software/yoyo/latest/)
— миграции лежат в `src/sound_loops/migrations/`, каждая пронумерована и
применяется ровно один раз, факт применения yoyo фиксирует сам (таблицы
`_yoyo_*`). Новое изменение схемы — это новый файл в этой папке, а не
правка существующего.

## Куда класть лупы и музыку

Всё содержимое `data/` в `.gitignore` — эти файлы не попадают в репозиторий.

- **Лупы** — готовые mp4 в `data/loops/` (можно вложенно). Готовятся
  вручную вне проекта: 3–11 секунд, без аудиодорожки. Код их не создаёт и
  не изменяет, только сканирует и читает метаданные через ffprobe. Файл,
  который не подходит под эти условия (не читается, с аудио, не в
  диапазоне длительности), логируется и пропускается — прогон из-за него
  не падает.

- **Музыка** — подмножество `fma_small` датасета [FMA (Free Music
  Archive)](https://github.com/mdeff/fma): 8000 тридцатисекундных mp3.
  Ожидаемая раскладка после распаковки:
  `data/raw/fma_small/000/000002.mp3` — mp3 разложены по трёхзначным
  подпапкам, имя файла — шестизначный ID трека. Метаданные — отдельно,
  `data/raw/fma_metadata/tracks.csv`. Для итерации 0 достаточно 200–300
  mp3, распаковывать весь архив (7+ ГиБ) не обязательно — можно взять
  несколько подпапок.

  Перед скачиванием стоит прикинуть место на диске: `fma_small.zip` — это
  ~7,2 ГиБ, `fma_metadata.zip` — ~342 МиБ. Если нужны не все файлы,
  оба архива поддерживают HTTP Range-запросы, и нужную часть можно
  скачать без загрузки архива целиком.

## Команды

```bash
make sync      # установить зависимости проекта
make init-db   # создать базу и схему (идемпотентно)
make ingest    # просканировать data/loops и data/raw,
               # заполнить таблицы, напечатать статистику
make render    # случайный луп + случайный отрезок трека -> data/renders/*.mp4
make render-loop LOOP=data/loops/my_loop.mp4  # рендер для конкретного лупа
make index      # посчитать эмбеддинги треков, у которых их ещё нет (CLAP)
make tag-tracks # темп + zero-shot теги для треков без атрибутов (нужен index)
make search QUERY="sad piano"                      # найти и напечатать топ-5
make search QUERY="sad piano" EXPORT=data/found     # + скопировать в data/found для прослушивания
make clap-check  # проверка вменяемости: текстовая башня CLAP не схлопнута
make match-loop LOOP=data/loops/my_loop.mp4 [FILTERS=1] [RERANK=1]  # см. «Гибридный поиск»
make ui        # веб-интерфейс агента — см. «Агент и веб-интерфейс»
make test      # прогнать тесты
make lint      # прогнать линтер
make clean     # удалить .venv и кэши тестов/линтера
```

Каждая цель — тонкая обёртка над `uv run sound-loops ...` (см. `Makefile`).

`render` печатает путь к получившемуся файлу и сохраняет запись о рендере
в базу. `index`/`search` — см. раздел «Поиск музыки по тексту» ниже.

## Модель данных

- **loops** — путь, длительность, разрешение.
- **tracks** — путь, длительность, метаданные из датасета (название,
  исполнитель, жанр — могут быть пустыми, если разбор `tracks.csv` не
  удался; это не ошибка), и с итерации 1 — `embedding` (`vector(512)`,
  HNSW-индекс по косинусной метрике) и `embedding_model` (какой чекпоинт
  его посчитал). Отдельной таблицы под эмбеддинги нет: у трека их ровно
  один на актуальную модель, `embedding_model` нужен только чтобы при
  смене чекпоинта было видно, что в колонке лежит устаревшее значение —
  `index` пересчитает такие треки заново. С итерации 4 — `tempo_bpm`
  (librosa) и `tags` (`jsonb`: числа косинусной близости по категориям
  `vocals`/`mood`/`genre`, не победившая метка) и `attrs_version` (версия
  набора фраз/логики темпа, см. «Гибридный поиск» ниже).
- **renders** — какой луп с каким треком склеен, координаты вырезанного
  отрезка (`track_id`, `start_seconds`) и куда сохранён результат.
  Отдельной таблицы под отрезки нет: координаты вычисляются на лету при
  рендере и используются ровно один раз, так что хранить их отдельно от
  самого факта рендера незачем.

Путь — естественный ключ уникальности для лупов и треков: повторный
запуск `ingest` обновляет существующие строки, а не создаёт дубликаты.

С итерации 5 в той же базе есть ещё и таблицы Postgres-чекпойнтера
LangGraph (`checkpoints`, `checkpoint_writes`, `checkpoint_blobs` и
т.п., см. «Агент и веб-интерфейс» ниже) — они не часть этой модели
данных, заводятся отдельно от yoyo-схемы (`PostgresSaver.setup()` в
`init-db`) и хранят состояние сессий агента, а не домен проекта.

## Как собирается превью

При рендере выбирается случайный трек, которого хватит на длительность
лупа, и внутри него — случайная точка начала (без привязки к какой-либо
сетке). Аудио вырезается ровно под длительность лупа, с короткими
фейдами на входе и выходе (иначе на срезе слышен щелчок). Видеопоток не
перекодируется — луп подшивается как есть, а итоговую длительность
определяет видео: если аудио оказалось длиннее, лишнее обрезается.
С ffmpeg/ffprobe работа идёт через subprocess плоскими списками
аргументов — команду легко скопировать и повторить в терминале.

## Поиск музыки по тексту

Треки превращаются в эмбеддинги через [CLAP](https://github.com/LAION-AI/CLAP)
(`transformers.ClapModel`/`ClapProcessor`. Чекпоинт — **`laion/larger_clap_general`**.
Устройство по умолчанию — MPS, при ошибке автоматически
откатывается на CPU (`CLAP_DEVICE` в `.env`, если нужно зафиксировать CPU
сразу). Первый запуск качает веса с HuggingFace Hub; дальше, если чекпоинт
уже в `~/.cache/huggingface`, каждый последующий `index`/`search`/`clap-check`
работает полностью офлайн — `hf_cache.py` сам выставляет `HF_HUB_OFFLINE=1`
(иначе `transformers` на каждый запуск лишний раз стучится в сеть сверяться
с последней ревизией репозитория, даже когда веса уже скачаны).

```bash
make index                                        # посчитать эмбеддинги новых/непроиндексированных треков
make search QUERY="sad piano"                     # топ-5 в терминал: похожесть, название, путь
make search QUERY="sad piano" EXPORT=data/found    # + скопировать в data/found для прослушивания
make clap-check                                    # проверка вменяемости: текстовая башня не схлопнута
```

`index` берёт из `tracks` записи без эмбеддинга **или** с эмбеддингом от
другого чекпоинта (`embedding_model` хранит, какой именно), декодирует
аудио через ffmpeg (`-f f32le` на stdout), считает эмбеддинги батчами и
коммитит после каждого батча — если процесс прервать, уже посчитанное не
теряется, а следующий запуск подхватит только оставшееся.

**Эмбеддинг всегда считается по первым `CLAP_MAX_AUDIO_SECONDS` (10с по
умолчанию) трека, не по всему файлу.** Причина: у `ClapFeatureExtractor`
дефолт `truncation="rand_trunc"`/`max_length_s=10` — для входа длиннее
модель сама берёт случайные 10 секунд, и эмбеддинг меняется от запуска к
запуску (поймали это численно в разделе «Эвалы» ниже: 0.098 косинусной
близости между двумя эмбеддингами одного и того же файла). `decode_audio_mono`
обрезает вход до этой границы сам (`ffmpeg -t ...`), поэтому до `rand_trunc`
дело не доходит вообще — эмбеддинг детерминирован (проверено: 1.0000).
Добавлять свою музыку можно любой длины, обрезать вручную перед `ingest`
не нужно.

`search` считает эмбеддинг запроса, ищет ближайшие по косинусной близости
через HNSW-индекс (`embedding <=> ...`, `pgvector`) и печатает похожесть
вместе с путём к файлу — но по цифрам «грустное» от «эпичного» не отличить,
поэтому `--export-dir`/`EXPORT=` существуют специально для прослушивания.

**Проверка вменяемости** (см. `docs/sound_loops-iteration-1.md`): `clap-check`
считает попарные косинусные близости нескольких заведомо непохожих фраз —
если все около 0.99, текстовая башня схлопнута и чекпоинт непригоден. На
чекпоинте `laion/larger_clap_general` они лежат в диапазоне 0.06–0.27 —
башня не схлопнута.

Вторая часть — ручная: прогнать контрастные запросы и послушать топ-N через
`EXPORT=`. Прослушано на `fma_small` (268 треков) на запросах вроде «sad
slow piano», «female operatic vocal», «fast aggressive electronic dance
music»: **выдача осмысленна** — треки в топе соответствуют текстовому
описанию, для разных по смыслу запросов выдача не пересекается.

## Эвалы (итерация 3)

Пока качество подбора оценивалось на глаз. Эвал делает измеримым то, что
уже есть, и даёт baseline, с которым сравниваются дальнейшие изменения
(фильтр по темпу, нарезка по тактам и т.д.) — см.
[docs/sound_loops-iteration-3.md](docs/sound_loops-iteration-3.md).

**Разметка** — `evals/dataset.json`, один файл в git (не в базе, правится
вместе с кодом). Список объектов:

```json
[
  {
    "loop": "data/loops/loop-1.mp4",
    "setting": "nature",
    "tempo": "slow",
    "mood": ["calm", "dreamy"],
    "vocals": "instrumental",
    "good_tracks": [
      "data/raw/fma_small/000/000002.mp3",
      "data/raw/fma_small/000/000123.mp3"
    ]
  }
]
```

`setting`/`mood` — те же фиксированные категории, что в схеме шага A
([vlm.py](src/sound_loops/vlm.py)); `good_tracks` — 1-3 пути к трекам,
найденные вручную через `make search QUERY="..."` (слушать выдачу,
отмечать удачные) — 2-3 предпочтительнее одного, hit@k с единственным
известным позитивом заметно шумнее. Разметка проверяется pydantic-схемой
([eval_dataset.py](src/sound_loops/eval_dataset.py)) при каждой загрузке —
опечатка в категории настроения падает с понятной ошибкой, а не тихо
игнорируется. **Разметка руками — это на пользователе**, автоматически
её не сгенерировать (нужно слушать треки и смотреть видео). В
`data/loops/` 30 лупов, набор размечен полностью
(быстрые/медленные, разное настроение, люди/животные/природа/город).

**Команды**:

```bash
make eval-run                               # прогнать весь набор, напечатать метрики, сохранить в evals/runs/
make eval-run-loop LOOP=data/loops/loop-1.mp4  # то же для одного лупа — для отладки
make eval-compare A=evals/runs/x.json B=evals/runs/y.json  # разница между двумя прогонами
make blind-eval                             # слепое сравнение пайплайна со случайным baseline
```

`eval-run` требует, чтобы `analyze` уже был прогнан на лупах набора (та же
логика кеша, что у `match` — шаг A не дублируется, а переиспользуется как
есть). Метрики:

1. **Понимание видео** — пересечение множеств `mood` (Jaccard) и точность
   `setting` против разметки: если VLM систематически путает настроение,
   чинить нужно промпт шага A, дальше можно не идти.
2. **Качество запроса и поиска** — `hit@1`/`hit@5` (попал ли размеченный
   трек в топ-N выдачи по музыкальному запросу пайплайна) и средний ранг
   лучшего из размеченных. Основная автоматическая метрика итерации;
   абсолютное значение мало что значит (в библиотеке наверняка есть
   неразмеченные треки не хуже), а вот **изменение между прогонами** —
   значит много.

Оба вызова модели в `eval-run`/`blind-eval` всегда идут с `temperature=0`
(независимо от `VLM_TEMPERATURE` в `.env`) — иначе часть разницы между
прогонами была бы случайностью семплирования, а не изменением кода.
Прогон сохраняется в `evals/runs/<метка_времени>_<коммит>.json` вместе с
моделью, версией промпта и параметрами поиска — без этого через пару
недель не понять, чем прогон от одной даты отличается от другого.

`eval-compare` показывает разницу и по агрегатам, и по каждому лупу —
**ухудшившиеся лупы выводятся первыми**: средняя метрика может остаться
на месте, когда половина набора улучшилась, а половина сломалась, и без
построчного сравнения такое изменение выглядит безобидным.

`blind-eval` — метрика 3, итоговое качество. Для каждого лупа набора
собирает два превью (`match_once` — пайплайн, `render_once` — случайный
baseline), спрашивает в терминале, какое лучше, без подсказки, что есть
что, и складывает ответы в `evals/blind_runs/`. Головная цифра — доля
побед пайплайна среди решительных ответов (без учёта ничьих). Это
получасовая процедура, есть смысл гонять её после заметных изменений, а
не на каждый прогон.

**Baseline** (2026-09-16, коммит `9631181`, промпт `v8`, 30 лупов,
`evals/runs/20260916T140720_9631181.json`):

| метрика | значение |
|---|---|
| setting accuracy | 0.57 |
| mood overlap (mean) | 0.25 |
| hit@1 | 0.00 |
| hit@5 | 0.00 |
| mean best rank | 179.2 (не найдено в топ-500: 8/30) |

Слепое сравнение (2026-09-16, коммит `7ac817d`, `evals/blind_runs/20260916T091057_7ac817d.json`,
**измерено до обеих починок ниже** — числа для итогового качества
устарели относительно текущего кода, но фиксируем как первую точку):
**41% побед пайплайна** (9 из 22 решительных ответов, 8 ничьих) — хуже
случайного baseline'а.

`hit@k` практически на нуле не потому, что пайплайн ничего не находит
случайно — по ходу измерения нашли и починили два реальных бага:

1. **Эмбеддинги треков длиннее ~10с были недетерминированы.** `ClapFeatureExtractor`
   по умолчанию (`truncation="rand_trunc"`, `max_length_s=10`) берёт
   случайные 10 секунд из любого файла длиннее. Проверено эмпирически:
   один и тот же 697-секундный файл, посчитанный дважды, дал косинусную
   близость **0.098** между своими эмбеддингами — практически шум.
   Сначала обрезали только кураторские good_tracks (до 30с, как
   FMA-превью) — не помогло (219→207): 30с всё ещё длиннее 10-секундного
   окна CLAP, `rand_trunc` продолжал срабатывать. Настоящая починка —
   на уровне кода: `decode_audio_mono` теперь сам обрезает вход до
   `CLAP_MAX_AUDIO_SECONDS` (10с, `config.py`) **с начала файла**, до
   `rand_trunc` дело не доходит вообще. Переиндексировали всю библиотеку
   (830 треков, не только кураторские) — эмбеддинг детерминирован
   (проверено: **1.0000**). `mean best rank` подвинулся ещё (207→179) —
   в сумме с первого шага 219→179, но `hit@k` всё ещё 0.00, то есть
   и это не было главной причиной.
2. **Промпт шага A использовал не все категории.** VLM практически не
   предсказывала `mood`/`setting`, для которых в промпте не было
   few-shot примера (`epic`/`festive`/`tragic`, `abstract`/`performance` —
   ноль раз за 30 лупов), независимо от того, насколько они подходили по
   факту. Добавили примеры для пропущенных категорий и обобщили
   инструкцию «не дефолти» (раньше называла один конкретный дефолт,
   модель просто подменяла его на другой). `setting_accuracy` выросло
   0.50→0.57; `mood_overlap` не изменился — новые примеры для
   `tragic`/`festive` сами стали над-используемыми (классическое
   смещение к недавнему в списке), вытеснив ранее рабочий `melancholic`.
   Решили не докручивать дальше — на 30 лупах разница вряд ли значима.

Оставшийся низкий `hit@k` (0.00) после обеих починок — видимо реальное
свойство пайплайна на этом этапе, а не баг измерения: либо шаг A
ошибается ещё слишком часто (50-57% точность `setting`), либо у
одного размеченного трека на луп слишком шумная статистика, либо CLAP
слабо разделяет такие общие текстовые описания. Разбираться дальше —
на усмотрение следующей итерации.

**Ограничения**: набор в ~30 лупов и разметка одним человеком — это мало.
Разница в пару процентов между прогонами ничего не значит и гоняться за
ней не стоит. Метрики здесь ловят заметные сдвиги и явные поломки, а не
выжимают десятые доли процента.

## Гибридный поиск и переранжирование (итерация 4)

Поиск по итерации 1 — одно сравнение векторов, у треков нет читаемых
атрибутов. Итерация 4 (план: [docs/sound_loops-iteration-4.md](docs/sound_loops-iteration-4.md))
достраивает три слоя — фильтр по атрибутам, вектор, переранжирование
моделью — и честно измеряет, что из этого реально помогает.

**Атрибуты треков** — `make tag-tracks` (возобновляемая команда, как
`index`; нужен предварительный `index` — теги считаются по уже готовому
`tracks.embedding`, без повторного похода в CLAP за аудио):

- **Темп** — через `librosa.beat.beat_track` (`tempo.py`). Beat-tracking
  регулярно путает темп с половинным/двойным (октавная ошибка) —
  `normalize_tempo_octave` удваивает/делит пополам, пока темп не попадёт
  в разумный диапазон `[60, 200]` BPM. На реальной библиотеке (830
  треков) распределение вменяемое: медиана ~117 BPM, только 1 трек упёрся
  в нижнюю границу.
- **Теги** — zero-shot через CLAP: контрастные фразы (`tags.py`,
  `VOCAL_PHRASES`/`MOOD_PHRASES`/`GENRE_PHRASES`) сравниваются с уже
  посчитанным аудио-эмбеддингом трека. Хранятся числа косинусной
  близости, не победившая метка (топ-3 для mood/genre, обе фразы для
  vocals) — порог можно двигать без пересчёта. Точность тегов средняя
  (это ожидаемо — они читаемое описание для модели-переранжировщика, не
  истина в последней инстанции), но качественно они осмысленны (см.
  примеры объяснений ниже).

**Целевые атрибуты сцены**: диапазон темпа выводится из motion лупа
(`filters.py::MOTION_TEMPO_RANGES` — обычный словарь, от статики к хаосу
сдвигается вверх); вокал — отдельное поле в `MusicQuery` (шаг B,
`vlm.py`), а не слово внутри текста запроса — используется как фильтр, не
только как часть эмбеддинга. **Изначальные границы были взяты на глаз и
резко ухудшили retrieval** (см. «Результат» ниже) — переоткалиброваны по
факту: диапазоны темпа расширены до наименьших, что покрывают почти все
`tempo_bpm` размеченных good_tracks (было 18/30 несовпадений, стало
3/30 — оставшиеся 3 генуинные выбросы), а у фильтра по вокалу появился
`VOCALS_CONFIDENCE_MARGIN` — трек не исключается по вокалу, если разница
между его метками меньше медианного зазора по всей библиотеке (0.11 из
830 треков): числа тегов вокала местами очень шумные (доли 0.01–0.05,
иногда отрицательные), и на таком зазоре бинарное решение — почти
случайность. Калибровка — по данным всей библиотеки, не подгонка под
эти конкретные 30 размеченных лупов (это было бы переобучением на
тесте).

**Гибридный поиск** (`search_tracks_hybrid`, `search.py`): SQL-фильтр по
`tempo_bpm`/`tags->vocals` → векторное ранжирование остатка. **Лестница
послаблений** (`filters.py::relaxation_ladder`) — если строгие условия
дают пустую выдачу, по порядку: расширить диапазон темпа (×1.5) → снять
требование по вокалу → снять все фильтры. Каждый примененный шаг
попадает в вывод (`match --filters` печатает его, `eval-run --filters`
пишет в JSON и агрегирует «лупов с послаблением»).

**Переранжирование** (`rerank.py`, `--rerank`): топ-3 кандидата (не
топ-10 — на 4B-модели длинный список ухудшает выбор) отдаются модели
вместе с их атрибутами (темп, теги, similarity) и описанием сцены;
модель выбирает одного и коротко объясняет выбор — объяснение печатается
всегда (`match --rerank`). Разбор ответа (`clamp_candidate_index`)
откатывается на топ-1 по вектору, если модель вернула номер вне
диапазона.

Всё переключается параметрами CLI, а не правкой кода:
`sound-loops match/eval-run/blind-eval --filters --rerank` (или
`--no-filters`/`--no-rerank`, по умолчанию оба выключены — совпадает с
поведением итерации 3).

### Результат

Шесть конфигураций прогнаны через `eval-run` на том же наборе из 30
лупов (2026-09-17, промпт `v8`, `eval_search_depth=500`). Метрика —
`mean_penalized_rank`, не `mean_best_rank`: **важная методологическая
поправка, см. ниже**, старое среднее нечестно сравнивало конфигурации с
разным числом "не найдено".

| конфигурация | коммит | penalized rank | не найдено в топ-500 |
|---|---|---|---|
| старый промпт B, без фильтров (baseline) | `30cf5de` | 276.1 | 7/30 |
| старый промпт B, откалиброванные фильтры | `13f0a55` | 258.1 | 9/30 |
| старый промпт B, фильтры + реранк | `13f0a55` | 258.1 | 9/30 |
| **новый промпт B, без фильтров** | `2f5b928` | **256.6** | 8/30 |
| новый промпт B, фильтры | `2f5b928` | 284.1 | 10/30 |
| новый промпт B, фильтры + реранк | `2f5b928` | 284.1 | 10/30 |

(`setting accuracy`=0.57, `mood overlap`=0.25, `hit@1`=`hit@5`=0.00 —
одинаковы во всех шести, шаг A не менялся ни разу.)

**Путь до этой таблицы — три отдельные находки, каждая проверена данными,
а не на глаз:**

**1. Калибровка фильтров.** Первый прогон с диапазонами темпа "на глаз"
дал регресс (не найдено 7→18/30). Сопоставил предсказанный диапазон с
*настоящим* `tempo_bpm` `good_tracks` и с ручной разметкой `tempo`
(slow/mid/fast) — разметка почти не разделялась по измеренному BPM
(медианы 83–172/86–185/86–129 для slow/mid/fast). Расширил диапазоны до
наименьших, что покрывают 27/30 good_tracks (было 18/30). Из
оставшихся несовпадений большинство оказались фильтром по **вокалу**,
не темпу — сами числа CLAP-тегов вокала у половины библиотеки
различаются меньше 0.11 (шум, не решение), добавил
`VOCALS_CONFIDENCE_MARGIN`. Итог на тот момент (со старым промптом B):
`mean best rank` 207.9→154.4, не найдено 7→9/30 — фильтры из регресса
стали измеримым улучшением.

**2. Диагностика retrieval.** Взял самый провальный луп (best_rank=496)
и напрямую сравнил в CLAP схожесть его размеченного good_track с (а)
реальным запросом шага B («folk, acoustic guitar») и (б) описанием,
построенным по собственным CLAP-тегам трека («piano, strings»):
схожесть 0.013 → 0.31, ранг 496 → 14. **CLAP работает нормально** — шаг
B угадывает не тот жанр/инструменты. Дальше проверил на всех 30: жанр
«electronic» выбран в 12+/30 без всякой статистической причины (в
библиотеке ровно по 100 треков на каждый из 8 жанров).

**3. Переписан промпт шага B** (`_MUSIC_SYSTEM_PROMPT`, `vlm.py`):
жанрам добавлена короткая характеристика (не просто название), явно
сказано, что electronic — не безопасный дефолт, примеры в промпте
разбросаны по разным жанрам, чтобы не создавать жёсткую ассоциацию
"эта обстановка → всегда этот жанр" (старый промпт для "nature, calm,
dreamy" почти дословно давал "folk, acoustic guitar" — именно это
скопировал шаг B и для домашней сцены). **Дешёвый контрольный
эксперимент перед этим**: убрать жанр из запроса вовсе (оставить только
настроение) — результат хуже baseline'а (mean best rank 252.9 против
207.9), это исключило гипотезу "жанр вообще не нужен". Новый промпт:
без фильтров `mean_penalized_rank` 276.1→256.6 — лучший результат из
всех шести конфигураций, хотя далеко не идеальный: построчно 12/30
лупов улучшились (иногда сильно, 496→40 и 472→13), 11 стали хуже (в
том числе 2 полностью пропали), 1 нашёлся впервые, 6 остались
ненайденными, как и были — чистого улучшения без потерь не бывает.

**4. Фильтры и реранк на новом промпте не помогают — а слегка вредят**
(256.6 без фильтров → 284.1 с ними — худшая конфигурация из всех шести).
Разгадка: фильтры компенсировали плохие жанровые угадывания старого
промпта, дополнительно сужая выдачу. Когда шаг B сам стал точнее,
компенсация больше не нужна, а собственные несовершенства фильтра
(единичные, но настоящие несовпадения по темпу/вокалу) начали
перевешивать остаточную пользу.

**Что осталось честно нерешённым:**

- И на старом, и на новом промпте есть **горстка лупов, где фильтры
  реально мешают** — генуинные выбросы по темпу/вокалу, расширять
  диапазоны дальше означало бы фактически убрать фильтр целиком.
- **Лестница послаблений почти не проверена нагрузкой** — на
  `eval_search_depth=500` не срабатывает практически никогда (строгий
  фильтр редко даёт пустую выдачу на такой глубине), на боевом
  `top_n=3` сработала 1 раз из 30 в отдельной проверке. Механика
  корректна (юнит-тесты + этот единичный живой случай), но не
  нагружена по-настоящему ни разу.
- **Переранжирование не изменило ни одной метрики ни в одном из трёх
  сравнений "с реранком/без"** — оно видит только топ-3 по вектору, а
  размеченный трек даже после улучшений в среднем далеко за пределами
  топ-70. Объяснения модели качественно разумны (ссылаются на
  темп/теги/сцену), но это не то же самое, что измеримая польза.
- **Правка промпта помогла в среднем, но не для каждого лупа** — 11 из
  30 стали хуже (из них 2 полностью пропали). Это не повод откатывать
  правку (агрегат заметно лучше), но и не история безусловной победы.

**Методологическая поправка, найденная по ходу**: `mean_best_rank`
усредняет только *найденные* лупы — конфигурации с разным числом "не
найдено" через него сравнивать нечестно (выживаемость смещает среднее в
пользу той, что больше отбросила; именно так первая версия фильтров на
новом промпте — 176.2 по старой метрике — выглядела почти как старая
версия фильтров на старом промпте — 154.4 — хотя по факту одна из них
однозначно хуже baseline'а). Добавлена `mean_penalized_rank`
(`eval_metrics.py::penalized_rank`, `EvalAggregates`) — не найдено
считается как `search_depth`, а не выбрасывается; печатается в
`eval-run` рядом со старой метрикой, участвует в дельте `eval-compare`.
Старые сохранённые прогоны (без этого поля) не стали нечитаемыми —
`load_run` досчитывает его при загрузке.

**Итоговый вывод**: самый большой рычаг этой сессии — не гибридный
поиск и не переранжирование, а исправление того, что искал шаг B.
Фильтры полезны только когда компенсируют слабый upstream-сигнал; когда
upstream исправили, фильтры стали чистым минусом. **Текущая
рекомендация: `--filters`/`--rerank` не включать** (в CLI они и так по
умолчанию выключены — менять умолчания не потребовалось). Переранжирование
остаётся архитектурно оправданным (RAG в чистом виде, читаемые
объяснения), но недоказанным на этом наборе ни разу за все прогоны.

## Агент и веб-интерфейс (итерация 5)

До сих пор пайплайн был линейной цепочкой: запустил — получил один
результат. Итерация 5 (план: [docs/sound_loops-iteration-5.md](docs/sound_loops-iteration-5.md))
превращает её в граф [LangGraph](https://langchain-ai.github.io/langgraph/)
с состоянием: поиск музыки становится инструментом, который модель
вызывает сама, результатов снова три (не один, как с итерации 2 — тогда
выбирать было некому), а после показа граф останавливается и ждёт текст
пользователя. Финальная MVP-итерация проекта.

```bash
make ui   # или: sound-loops ui
```

**Модель осталась одна** — `qwen3-vl:4b-instruct`. Важная деталь: среди
vision-моделей в Ollama она — исключение, совмещает зрение и вызов
инструментов в одной модели; большинство vision-моделей на запрос со
списком инструментов отвечают ошибкой "not supported". Значит, для узла
`plan` не нужна отдельная текстовая модель — та же самая, что смотрит на
кадры лупа в узле `analyze`.

### Граф

```
analyze -> plan -> rerank -> render -> feedback --[текст, круг < лимита]--> plan
                                            |
                                            +--[иначе]--> конец
```

- **analyze** — кадры лупа + motion → описание сцены (тот же кеш
  `video_analyses`, что у команды `analyze`), один раз на видео.
- **plan** ([agent_planner.py](src/sound_loops/agent_planner.py)) — модель
  сама вызывает инструмент `search_music` (query, диапазон темпа, вокал,
  top_n), пока не наберёт 3 разных запроса. **Резервный путь**: если
  модель дважды подряд не вызвала инструмент, следующий слот закрывается
  тем же надёжным `compose_music_query`, что был в итерации 2 — не разбор
  свободного текста ответа модели (парсинг текста хрупкий, этого же
  принципа проект держится и для обратной связи, см. ниже).
- **rerank** — та же функция итерации 4, по отдельности для каждого из 3
  пулов кандидатов, с дедупликацией: если пул одного слота отдаёт трек,
  уже занятый другим слотом этого круга, берётся следующий кандидат.
- **render** — 3 превью вместо одного, той же функцией, что раньше
  собирала один (`render.py::render_preview`).
- **feedback** — штатный `interrupt()` LangGraph: граф останавливается
  между вызовами `graph.invoke()`, а не крутит собственный цикл ожидания.
  Текст пользователя **не разбирается** отдельным узлом — складывается в
  состояние как есть и передаётся `plan` вместе с историей запросов и
  списком уже отвергнутых треков (важно передавать именно отвергнутое, а
  не только новое пожелание — иначе модель ходит по кругу).

**Лимит кругов обязателен** (по умолчанию 3, `AGENT_MAX_ROUNDS`) — без
него связка «модель формулирует запрос → пользователь недоволен → снова»
крутилась бы до собственного предела рекурсии LangGraph, упираться в
который некрасиво. Условное ребро уходит в конец, даже если пользователь
написал текст, как только круг достигнут.

**Состояние живёт в Postgres** ([langgraph-checkpoint-postgres](https://github.com/langchain-ai/langgraph)),
не в памяти процесса — сессия идентифицируется `thread_id` и переживает
перезапуск интерфейса. Таблицы чекпойнтера заводятся отдельно от
yoyo-схемы проекта (`init-db` вызывает `PostgresSaver.setup()`) — это
инфраструктура LangGraph, не доменная модель.

### Интерфейс

Gradio, одна страница: загрузка видео или выбор из `data/loops`, кнопка
запуска, три плеера с превью, счётчик кругов, поле обратной связи и
раскрывающийся блок «Что решила модель» — какую сцену увидела VLM, какие
3 запроса сформулировала, почему выбраны именно эти треки. Без объяснений
интерфейс выглядит случайным генератором, с ними видно логику.

### Результат

Итерация принята: граф работает как единое состояние с обратной связью,
поиск — инструмент, а не жёстко зашитый шаг, интерфейс запускался вручную
целиком (загрузка лупа из библиотеки → 3 превью → текст «мрачнее, без
вокала» → новая подборка, все 3 новых запроса явно учли «no vocals»).

**Надёжность вызова инструмента на локальной 4B-модели** (30 лупов,
`eval-run --agent`, промпт `v8`, `evals/runs/20260917T145653_940b388.json`):
**90 из 90 вызовов (100%) — модель сама вызвала `search_music` три раза
на каждом лупе, резервный путь не сработал ни разу.** Это лучше, чем
план заранее закладывал (план допускал, что 4B-модель может оказаться
ненадёжной, и предлагал `qwen3:4b` как запасной вариант для узла `plan` —
менять модель не понадобилось).

`hit@k` для агента считается по **объединению кандидатов всех 3 query**
(дедуп по треку, лучшая позиция побеждает) — трек засчитан найденным,
если попал в top-k хотя бы одного из трёх поисков. Сравнение с лучшей
конфигурацией итерации 4 (новый промпт B, без фильтров) на том же наборе:

| конфигурация | mean penalized rank | не найдено в топ-500 |
|---|---|---|
| итерация 4: новый промпт B, без фильтров | 256.6 | 8/30 |
| **итерация 5: агент, объединение 3 query** | 271.2 | **2/30** |

(`setting accuracy`=0.57, `mood overlap`=0.25, `hit@1`=`hit@5`=0.00 —
одинаковы, шаг A не менялся.) Средний штрафованный ранг чуть хуже
(+14.6) — но **лупов, для которых вообще ничего не нашлось в топ-500,
стало в 4 раза меньше** (`eval-compare`, построчно): три разных query
почти всегда находят *что-то* в разумной глубине, но не концентрируют
именно размеченный трек ближе к вершине выдачи сильнее одного хорошего
query — ожидаемый компромисс диверсификации, не баг измерения. `hit@1`/
`hit@5` на нуле в обеих конфигурациях — то же известное ограничение
итерации 3/4 (см. выше), не новое для агента.

**Известные ограничения:**

- Обратная связь проверена вручную (один прогон через интерфейс), не
  автоматическим тестом с реальной моделью — граф тестируется без Ollama
  (`FakeSceneAnalyzer.set_tool_call_turns`, см. CLAUDE.md), тот же принцип,
  что `blind-eval` не гоняется в CI.
- **Демо не записано** — план требует короткое видео работы интерфейса
  для README; сделано вручную через браузер (см. эту сессию), но
  файл записи ещё предстоит сохранить и приложить отдельно.
- UI держит одно долгоживущее соединение к базе на весь процесс — годится
  для локального однопользовательского MVP, не для нескольких
  параллельных пользователей (пул соединений не заводили, это было бы
  преждевременной сложностью на этом этапе).
- Три роли для трёх query («прямое попадание», «то же по энергии, другой
  жанр», «контраст») из плана не реализованы — на реальных прогонах
  подборка не выглядела однообразной без них (см. лог выше — модель сама
  тяготеет к разным жанрам), вводить усложнение впрок не стали.

**Что осталось за пределами MVP**: пул соединений для нескольких
одновременных пользователей интерфейса, автоматическая проверка влияния
обратной связи в CI (нужен реальный Ollama), явные роли для трёх query,
агент, который сам решает использовать фильтры по темпу/вокалу
осмысленно (сейчас это просто необязательные поля инструмента).

## Тесты и линтер

```bash
make test
make lint
```

Тесты используют настоящий Postgres — отдельную базу `<имя_рабочей_базы>_test`
в том же локальном инстансе, что и рабочая (та же строка подключения из
`.env`, только имя базы с суффиксом `_test`). База и схема создаются
автоматически при первом запуске тестов; перед каждым тестом, которому
нужна база, все таблицы очищаются — тесты не зависят друг от друга и от
состояния рабочей базы.

Реальных лупов и датасета не требуется — видео и аудио для тестов
генерируются самим ffmpeg (`lavfi`). Каждая уникальная пара (тип,
длительность) кодируется один раз за сессию pytest и кэшируется —
тесту, которому нужен файл под своим именем/путём, отдаётся копия
закэшированного файла, а не свежий энкод (см. `get_silent_loop`/
`get_tone_track` в `conftest.py`). Проверяется: длительность вырезанного
аудио и наличие обоих потоков в склеенном файле, что случайная точка
начала отрезка всегда попадает в допустимые границы трека, разбор
`tracks.csv` (в том числе отсутствующий/битый файл), валидация конфига,
идемпотентность `init-db` и `ingest`, и что `render`, повторённый
несколько раз подряд, каждый раз создаёт ровно одну новую строку в
`renders`.
